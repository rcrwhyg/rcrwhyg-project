# 朴素的启程：从一台 2C2G 服务器开始

> **摘要**: 本文是个人公众号与个人网站的开篇之作。作者从一台原本用于 WebRTC 信令测试的闲置 2C2G 阿里云轻量服务器出发，思考如何让有限资源产生价值。决定不用现成建站工具，而是亲手搭建一个 Rust + Leptos + PostgreSQL 的全栈个人站，并将公众号作为内容起点，逐步扩展为统一的数据枢纽。本文记述了这一朴素启程背后的动机与最初的技术选型思考。

## 引子：一台闲置的 2C2G

建立个人公众号和个人网站的想法是刚刚才有的。起因很简单：手头上有一台 2C2G 配置的轻量云服务器。在这个动辄微服务、分布式的时代，2C2G 显得非常局促，甚至有些寒酸。如果放任它吃灰，未免有些可惜；但如果用来跑一些重型应用，它又有些力不从心。

购买这个云服务器的起因是当时在做 WebRTC 信令服务器开发，为了学习与开发测试方便需要一台云服务器做 TURN 中继，在阿里云以很实惠的价格购买了一台 2C2G 40G 配置的轻量云服务器。后来就闲置了，但由于可以原价续费就一直保留着。

最近突然想起还有个云服务器，就开始思考：拥有一台 2C2G 的服务器，能做点什么？

将自己的想法和 GPT 聊了聊，最后决定动手搭建一个个人网站，并以此为契机，把过程中的学习、踩坑和技术思考记录下来。

## 以微信公众号为起点，构建个人数据枢纽

我并不打算只是简单地使用现成的建站工具（比如 WordPress 或者 Hexo）来做个人网站的搭建。作为一名开发者，尽可能的亲自动手搭建，灵活可控，任何天马行空的想法都可以尝试。

目前的构思：

- **起点：以微信公众号作为起点。** 这里的编辑器足够好用，也方便在手机端预览和分享。
- **数据同步：** 在 2C2G 的服务器上编写一个后台服务，定时通过微信官方 API，将公众号上发布的内容、排版甚至图片，同步/爬取到个人网站数据库中。
- **后续扩展：** 个人网站将作为统一的展示站点。将来如果有想法，希望个人网站还可以方便、平滑地接入其他平台的数据（比如知乎、小红书等）。

## 技术选型：为什么是 Rust + Leptos？

在决定自己写代码建站后，技术选型就比较重要了。面对 2C2G 40G 硬盘的捉襟见肘，主流的 Java 或繁重的 Node.js 方案可能会让内存长期处于告警状态，在我当前熟悉（或想学习）的技术栈中有很多现代方案可以选择：看起来 Go 可以担得起重任，Bun.js 或许也可以尝试，虽然也可以使用 Zig 或者 Moonbit 但它们在现在看来还比较年轻，所以我觉得这时候选择使用 Rust 就变得很顺理成章了。

经过权衡，确定了以下技术栈：

1. **后端与底层框架：Rust + Axum + Tokio**

   选择 Rust 在于它极低的内存占用和极高的运行效率。编译后的二进制文件跑在 2C2G 的机器上，不仅绰绰有余，甚至能让人体验到丝滑的快感。严苛的编译器也能帮助将大部分问题在上线前暴露并解决。

2. **前端展示：Leptos (SSR)**

   这是一个基于 Rust 的全栈/前端框架。选择它，一方面是为了保持前后端语言的统一（All in Rust）；另一方面，它的服务端渲染（SSR）能力不仅对搜索引擎（SEO）非常友好，还能在服务器端直接组装好 HTML 返回给浏览器，提升首屏加载速度。

3. **架构设计：单机单服务 + PostgreSQL**

   不需要任何过度设计的念头，没有微服务，没有复杂的中间件，就是一个极其朴素的"单机单服务（Monolith）"架构。配合轻量化的 PostgreSQL 数据库存储文章文本，再辅以云对象存储（OSS）来解决微信图片防盗链和本地磁盘不足的问题。

简单，粗暴，但足够有效。

## 总结

### 核心要点

1. **从闲置资源出发**：2C2G 不是限制，是"克制设计的契机"，逼出更朴素的架构选择
2. **公众号是入口，个人站是数据枢纽**：用代码而不是工具搭建，为后续多平台扩展留出空间
3. **Rust + Leptos + PostgreSQL = 现代化 All-in-Rust 栈**：低内存、高性能、SSR 友好、SEO 友好
4. **Monolith 优先**：在没有规模压力之前，单进程单服务比微服务更省心
5. **OSS 解耦图片**：把图片这种"重"资源放到云对象存储，VPS 只负责文本与编排
