# 文章措辞与文体规范

> 适用于 `articles/` 下全部个人网站首发稿。静态格式见 [specs/article-template.md](../specs/article-template.md)；质量清单见 [content-quality.md](./content-quality.md)。标杆范文：`articles/2c2g-server/06-ai-collab-engineering-lessons.md`（2026-08 定稿）。

## 总体基调

- **成熟、稳重**：工程复盘口吻，客观叙述，不口语化、不网络化。
- **读者是同行开发者**：假设读者具备基础技术背景，重点讲「为什么」与「如何落地」，而非教程式手把手。
- **第一人称克制**：可用「笔者」「本项目」「本次迭代」；避免「我觉得挺顺」「最尴尬的是」等情绪化表达。
- **结论先于感慨**：先陈述现象、根因、措施，再作简短归纳；不用感叹号堆叠语气。

## 推荐结构（实战复盘类，本项目常用）

1. **背景**：问题域、约束条件、迭代范围（一两段）
2. **问题 N**：现象 → 根因 → 可行方案（每节独立，标题用「问题一 / 教训一」等编号）
3. **落地**：对应仓库文件、规则、ADR、门禁脚本（写清路径）
4. **总结**：编号要点 + 一句收束（流程约束优于单次表现）
5. **参考资料** + **版本信息** + **版权声明**

目录优先用编号列表（`1. [章节](#anchor)`），便于公众号与个人站渲染一致。

## 措辞：推荐 vs 避免

| 避免 | 推荐 |
|------|------|
| 「我帮你干完了」「听起来挺顺」 | 「Agent 在未获本轮同意的情况下执行了 push」 |
| 「最尴尬的问题」 | 「主题切换在数版实现中均未生效」 |
| 「坑 1 / 坑 2」 | 「问题四 / 子节：现象与根因」 |
| 「是不是 leptos 坏」 | 「应区分框架缺陷与用法不当」 |
| 「兜底」（贬义叙事） | 「vanilla JS 在该场景更稳妥」或「分层职责」 |
| 大量 emoji 反思框（🪞 反思） | 必要时仅用 **💡 提示** / **⚠️ 注意**（每篇各 1–3 处） |
| 「5 轮里 AI 反复犯蠢」 | 「五轮迭代中反复出现同一类失误模式」 |

## 技术叙述

- **事实可查证**：版本号、tag、文件路径、命令须与仓库一致；不确定先查代码或 ADR，不凭印象。
- **版本信息行**：写清 Leptos / Axum / **Rust**（与 `rustc --version` 或 CI stable 对齐）/ 相关栈（如 Tailwind CSS 4.3.3）；注明写作年月；重大迁移注明 release tag 或 ADR 编号。
- **代码示例**：来自本仓库时注释 `// 见 path/to/file.rs`；禁止把未验证片段标为「已跑通」。
- **合集内文章**：修订栈版本时同步更新该合集全部文章的「版本信息」行（至少 Rust 小版本），避免前后矛盾。

## 与 AI 协作类文章的额外要求

- 写清 **deploy-gating**、**local-verification** 与仓库规则文件的对应关系。
- 区分「门禁通过」与「视觉 / 生产验收」——后者需单独描述（如 dev server 目视、CSS 体积门禁）。
- 第三方工具（Leptos、Tailwind、cargo-leptos）先评估用法，再下「工具是否有缺陷」的结论。
- 重大生产事故（如 CSS purge、CD 连续失败）按时间线写：现象 → 临时措施 → 终态方案 → tag/ADR。

## 审核与迭代

- 用户审核意见记入 `docs/article-reviews.md`。
- 措辞或结构大改后，更新本文件或 [content-quality.md](./content-quality.md) 中指向本规范的链接，便于 Agent 下一轮读取。
